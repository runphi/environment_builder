
- linux_vanilla: This patches are usefull when loading jailhouse in a kernel versione grater then 5.7 that is not been patched to run on jailhouse. However the kernel need the kprobe module enabled in the kernel config.
- omnv: the Omnivisor fork (628a02d8) on the KR260, applied with -d omnv (environment_cfgs/kr260-jailhouse.sh, JAILHOUSE_PATCH_ARGS); 0001-0003 are kria-jailhouse's (the KV260's), 0004 and 0005 are the KR260's:
  - 0001-pyjailhouse-the-Omnivisor-s-cell-header-and-cell_load.patch: pyjailhouse (used by "jailhouse cell linux" and the config tools) did not follow the Omnivisor's structures: its cell parser missed num_rcpu_devices and num_fpga_devices and read the memory regions 8 bytes off, its image loader looked for CONFIG_OMNV_FPGA in a config.h that does not exist (without importing os) to choose the cell_load layout, and used the ioctl number of the structure without the remote-CPU fields.
  - 0002-configs-kv260-linux-demo-the-Omnivisor-root-cell-s-ivshmem-links.patch: zynqmp-kv260-linux-demo.cell had another board's ivshmem configuration (memory, devices, INTx): now the links of the KV260 root cells, which the KR260 root cell has too (0004). The KR260 uses the KV260's demo cells: they only use resources of the K26 SOM.
  - 0003-arm64-zynqmp-return-all-the-results-of-forwarded-SIP-calls.patch: the root cell's firmware calls returned only the low 32 bits of x0, so every value Linux read from the firmware under Jailhouse was lost; now x0-x3.
  - 0004-configs-kr260-omnv-the-KV260-root-cell-s-memory-layout-no-FPGA-base-design.patch: the fork's KR260 root cell put the hypervisor at 0x7e000000, on its own ivshmem regions, and loaded a base design "system.bit" that does not exist (the Omnivisor has no DFX design for the KR260): now the hypervisor at 0x7f000000 as in the KV260 root cell (15 MB instead of 16, below the PMU firmware's pmu@7ff00000 reservation of the K26 SOM DT, which the KV260 root cell overlaps), and no base design.
  - 0005-arm-gic-v2-SPI-targets-of-cells-without-CPUs.patch: a cell with no CPU, only R5 cores, given an SPI (runPHI gives an R5 container with network its link's ivshmem INTx) had the SPI routed to no CPU: the hypervisor read the target of the cell's first CPU out of bounds (an empty CPU set), wrote 0 into the SPI's ITARGETSR byte and did not repair it when the SPI went back to the root cell, so every later cell on that ivshmem link got no interrupts until a reboot. Now the routing of a cell without CPUs is left alone, and an SPI that targets no CPU is retargeted. Not specific to the KR260: kria-jailhouse has the same code.
